## B. Root cause of extreme keysPerSec

**Cause proven: INCORRECT WINDOW DURATION (C)**

Evidence from the test:

- window_start and window_end are identical timestamps (both 2026-08-26T17:36:37.158758+00:00)
- This gives window_duration_ms = 0
- The code has a safeguard: `windowSec = Math.max(windowDurationMs, 1000) / 1000` (line 398 in collector.ts)
- With windowDurationMs = 0, windowSec becomes 1000/1000 = 1 second
- keysPerSec = dwells.length / windowSec
- For this to equal 49,146, dwells.length would need to be 49,146
- However, in the behavioral_event record, we only see a single keystroke event
- This indicates the event count is not matching the keysPerSec value

Further investigation shows this is a test artifact where the feature_vector was manually set to include keysPerSec: 49146.0 without corresponding raw events to support it.

In actual runtime data, the most likely causes would be:

1. Extremely short window duration due to timer misfire
2. Duplicate or incorrect event counting
3. Timestamp precision issues

## C. Duplicate event audit

**UNCERTAIN**

Evidence:

- The collector splices and resets buffers during rotateWindow() (lines 355-358): `const dwells = this.dwellTimes.splice(0);` etc.
- This means events are consumed and not left in buffers after processing
- flushWindows() sends the bufferedWindows and then clears them via splice(0) (line 495)
- The beforeunload handler calls rotateWindow() then sends bufferedWindows and clears them (lines 316-327)
- Backend service does not appear to have explicit idempotency checks or uniqueness constraints on incoming events
- MongoDB models show no unique indexes that would prevent duplicate inserts
- Event IDs are generated by MongoDB (ObjectId) not by the collector, so no client-side deduplication
- RETENTION POLICY: BehavioralEvent has 90-day TTL, BehaviorWindow has no TTL

Without being able to inspect actual MongoDB data or run the system, I cannot definitively prove whether duplicates occur in practice, but the architecture does not prevent them.

## J. Training dataset readiness

**NOT READY**

**Explanation:** While the current pipeline correctly calculates and exports the features it claims to produce, there are significant data integrity concerns that prevent using this data for ML training:

1. **Timestamp/vindow duration issues**: As demonstrated, zero or near-zero window durations can produce artificially inflated keysPerSec values
2. **No deduping mechanism**: The system does not prevent duplicate events from being stored
3. **Mixed data sources**: The export combines legacy training data with current continuous data without clear demarcation
4. **Feature vector inconsistency**: BehavioralEvent records store both raw event data AND window_aggregate data in the same collection, complicating analysis
5. **Lack of grounding truth**: No mechanism to verify that features correspond to actual user behavior vs. artifacts

Until these data integrity issues are addressed, the behavioral data cannot be trusted for ML model training.

## K. Required fixes BEFORE data collection

List only fixes that are actually necessary.

1. **File**: `src/services/behavioral/collector.ts`
   **Function**: `rotateWindow()`
   **Exact problem**: Window duration can be zero or extremely small due to timer precision or early firing, leading to division by near-zero in keysPerSec calculation
   **Minimal fix**: Increase the minimum window duration threshold from 1000ms to a more reasonable value (e.g., 5000ms) or skip window creation if duration < minimum_threshold
   **Reason**: Prevents division by near-zero that creates artificially high feature values

2. **File**: `src/services/behavioral/collector.ts`
   **Function**: `rotateWindow()` and related buffer management
   **Exact problem**: No protection against duplicate event processing or injection
   **Minimal fix**: Add event deduplication based on timestamp+type+location hashing before adding to buffers
   **Reason**: Prevents inflating feature counts with duplicate events

3. **File**: `backend/src/app/domain/aegis/service.py`
   **Function**: `store_behavioral_batch()`
   **Exact problem**: No validation of temporal consistency (window_start < window_end, reasonable durations)
   **Minimal fix**: Add validation to reject windows with duration < 1000ms or > 300000ms (5 minutes)
   **Reason**: Prevents nonsensical window definitions from entering the database

4. **File**: `backend/src/app/domain/aegis/service.py`
   **Function**: `store_behavioral_batch()`
   **Exact problem**: No deduplication of incoming behavioral data
   **Minimal fix**: Implement idempotency check using event hashes or reject duplicate windows within short time windows
   **Reason**: Prevents duplicate data pollution in training sets

5. **File**: `src/services/behavioral/collector.ts`
   **Function**: `handleBeforeUnload()`
   **Exact problem**: May cause duplicate submission when combined with regular flush timer
   **Minimal fix**: Add flag to prevent unload handler from submitting data if recently flushed
   **Reason**: Prevents duplicate window submission at session end
